# 日常运行日志

让操作人员能从日志判断“发生了什么、影响谁、为何失败、是否重试、结果如何”，同时避免噪声和敏感信息泄露。

## 工作流

1. 查找项目现有 logger、结构化字段、事件命名、请求/Trace ID 传递和日志测试；优先沿用现有约定。
2. 从业务与调用链选择真正需要观察的边界：服务启停、重要操作开始/完成/失败、外部依赖、后台任务、权限/校验失败、重试、降级和不可恢复错误。
3. 在最能说明结果的一层记录事件，避免调用方和被调用方重复记录同一失败。
4. 选择级别和上下文，检查敏感信息与高频路径。
5. 运行相关测试、静态检查或最小冒烟，并审查正常路径的日志量。

只有项目确实没有统一日志能力且当前任务需要时，才引入最小可复用封装；不要顺带建设与需求无关的完整日志平台。

## 级别与字段

- `DEBUG`：仅用于诊断细节，默认运行不应产生大量输出。
- `INFO`：重要且正常的生命周期或业务结果。
- `WARN`：异常但可恢复，或已进入重试、回退、降级。
- `ERROR`：操作失败且需要关注；已处理的正常业务拒绝通常不是错误。

按事件需要加入稳定、可检索的字段，例如 `request_id`、`trace_id`、`host_id`、`task_id`、操作名、结果、耗时、重试次数、依赖名和错误类别。记录摘要或标识，不记录大对象与原始载荷。

事件消息保持简短稳定，例如 `task_execution_completed`。把变化值放在结构化字段中，避免依赖难以检索的拼接文本。

## 安全与噪声约束

不得记录密码、令牌、私钥、Authorization/Cookie 全文、敏感个人数据、二进制内容或大段请求/响应。确需关联时使用掩码、摘要或不可逆标识。

避免：

- 每次循环、轮询或成功数据库读写都打 `INFO`；
- 同一错误在多层重复记录；
- 记录巨大对象、完整 SQL 参数或外部响应；
- 保留临时调试输出；
- 在日志中宣称成功而实际操作尚未完成。

## 完成条件

- 关键正常、失败、重试/降级路径可被定位。
- 级别、事件名和字段符合项目约定。
- 日志包含足够上下文但不泄露敏感数据。
- 高频正常运行不会产生明显重复或无用日志。
- 相关测试或最小运行检查通过。
