# 根因调试

目标是解释故障为何发生，并修复首个导致业务行为偏离的位置，而不是只处理最后报错的一行。

## 调试工作流

1. **界定症状**：记录期望、实际、影响范围、时间与环境；保留错误、日志、失败断言或截图等原始证据。
2. **稳定复现**：运行最小复现或最接近失败行为的测试。无法复现时，明确缺少的状态或证据，不把猜测当结论。
3. **追踪相关调用链**：从入口到失败点检查调用方、参数构造、状态初始化与变更、业务分支、配置、持久化和外部边界。只扩展到能解释故障的范围。
4. **定位首个偏差**：比较每个关键节点的业务不变量与实际值，区分根因、传播路径和最终症状。
5. **形成诊断**：说明调用链、证据、根因及为何局部绕过不能解决问题；存在不确定性时列出最小验证动作。
6. **设计回归测试**：覆盖触发条件、正确结果和重要边界，使测试能在修复前暴露问题。
7. **实施最小修复**：修改根因所在层及保持契约一致所必需的调用方，不做无关重构。
8. **验证**：先运行回归测试，再运行受影响组件的相关测试和构建；必要时验证跨服务或数据流。

用户只要求诊断时，在第 5 步报告并停止，不实施代码修改。

## 证据优先级

优先使用可复现测试、运行日志、实际请求/响应、数据库状态和代码路径。错误位置只是起点；如果上游提供了错误参数或状态，应修复上游契约。空结果或单次成功不足以证明不存在问题，先检查过滤条件、时序、缓存和环境差异。

## 修复约束

- 不吞掉异常、绕过校验、隐藏失败或破坏真实业务逻辑。
- 不为让测试通过而随意改变测试期望。
- 不一次修改多个无关模块。
- 不把“增加重试”当作数据、状态或契约错误的默认修复。
- 若根因需要产品决策、数据修复、外部权限或破坏性操作，报告证据并在该边界停止。

## 完成条件

- 根因、传播路径和用户可见症状能够由证据串联解释。
- 回归测试在修复后通过并覆盖原始触发条件。
- 受影响组件的相关测试与构建通过。
- 修复没有引入无关行为变化；未验证项和剩余风险已说明。
