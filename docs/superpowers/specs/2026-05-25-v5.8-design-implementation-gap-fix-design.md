# Aegis V5.8 设计-实现偏差修复设计文档

> 日期: 2026-05-25
> 状态: Draft
> 范围: 修复 v5.8 设计文档与代码实现之间的全部28项偏差

## 1. 背景与目标

v5.8 引入了动态 eBPF DetectionPackage 能力，设计文档定义了完整的架构、接口、数据库和前端规范。代码审查发现28项设计-实现偏差，按优先级分为：

- **P0** (5项): 安全/正确性关键缺失
- **P1** (10项): 功能完整性缺失
- **P2** (7项): 设计一致性偏差
- **P3** (6项): 前端/UX缺失

**目标**: 修复全部28项偏差，使代码实现与设计文档一致。

## 2. 关键决策

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 修复范围 | 全部28项 | 用户要求 |
| 实施策略 | 分层递进（L1→L2→L3→L4） | 依赖关系清晰，问题不跨层扩散 |
| Proto命名不一致 | 保持兼容，注释标注偏差 | 避免破坏现有客户端 |
| Agent模块拆分 | 按设计拆分为独立文件 | 可维护性 |
| Builder沙箱 | 直接容器内编译，仅源码危险helper扫描 | 用户决策，避免子容器复杂度 |
| 人工审核流程 | 新增 awaiting_review 状态 + 页面确认 | 设计要求 |
| 前端角色权限 | 前后端都做角色控制 | 安全性 |
| perf fallback | 实现 ringbuf 优先 + perf fallback | 兼容旧内核 |
| Server状态转发 | 改为 gRPC | 与架构图一致 |
| 限速策略 | 三级限速 + 超限自动禁用 | 设计要求 |
| 版本降级防护 | SemVer比较 + rollback例外 | 设计要求 |

## 4. L2 核心层：Builder修复 + Agent重构 + Server gRPC改造

### 4.1 Builder 修复

#### 4.1.1 SHA256 真实计算

`builder/internal/service/builder_service.go` 修改：

- `StartBuild` 编译打包后，对 `package.tar.gz` 计算 SHA256
- 使用 `crypto/sha256` + `io.Copy` 流式计算
- 填入 `BuildResult.PackageSHA256`

#### 4.1.2 Builder Image Digest

- 优先从环境变量 `BUILDER_IMAGE_DIGEST` 读取（docker-compose.yml 注入）
- 回退：尝试读取 `/proc/self/mountinfo` 中的 image layer digest
- 最终回退：空字符串（非 placeholder）

#### 4.1.3 构建输入校验

新增 `validateBuildInput(req *StartBuildRequest) error`：

1. YAML 解析校验：`package.yaml` 必须可解析，`schema_version`/`package_id`/`version` 必填
2. Package ID 一致性：`package.yaml` 中的 `package_id` 与请求一致
3. HookPlan 引用完整性：每个 hook 的 `attach_type`/`attach` 非空
4. 源码危险 helper 扫描：正则匹配禁止的 BPF helper 调用
   - 禁止列表：`bpf_probe_read_kernel`、`bpf_override_return`、`bpf_setsockopt`、`bpf_sk_redirect`
   - 匹配到任一 → 返回错误

#### 4.1.4 人工审核流程

- `StartBuild` 完成后，build status 设为 `awaiting_review`（非 `success`）
- 新增 `ReviewBuild` 方法：校验 build 存在且 status 为 `awaiting_review`，审核通过后 status → `success`
- `SignPackage` 前置条件：build status 必须为 `success`（即已审核）

#### 4.1.5 Build log 上传 MinIO

- `StartBuild` 中将 `exec.Command("clang", ...)` 的 stdout/stderr 捕获到 `bytes.Buffer`
- 编译完成后将日志上传至 MinIO：`detection-packages/{id}/{version}/build.log`
- `BuildResult` 中记录 `BuildLogObjectKey`

#### 4.1.6 Event Schema 生成

- 编译成功后，从 `plugin.yaml` 解析 `event_schema` 字段
- 序列化为 JSON 填入 `BuildResult.EventSchemaJSON`
- 若 `plugin.yaml` 无 `event_schema`，从 `.bpf.o` ELF sections 中提取 event struct 偏移信息生成基础 schema

#### 4.1.7 HookSummary 生成

- 编译成功后，从 `plugin.yaml` 解析 hooks 列表
- 对每个 hook，检查 `.bpf.o` 中对应 ELF section 是否存在
- 生成 `HookSummary` protobuf：hook name、attach_type、attach_point、program_size
- 填入 `BuildResult.HookSummaries`

#### 4.1.8 GetPackageBuildStatus RPC

- 新增 `GetPackageBuildStatus` 实现
- 从 workDir 中的 `.build_status.json` 文件读取构建状态
- 返回 build_id、status、error_message、progress_percent

#### 4.1.9 LLVM/libbpf 版本获取

- `GetBuilderInfo` 中执行 `clang --version`，解析版本号
- 执行 `bpftool version 2>/dev/null || echo "unknown"`，解析 libbpf 版本
- 填入 `GetBuilderInfoResponse.llvm_version`/`libbpf_version`

### 4.2 Agent 重构

#### 4.2.1 模块拆分

从 `manager.go` (499行) 拆分为6个文件：

| 文件 | 职责 | 关键类型/方法 |
|------|------|--------------|
| `manifest.go` | PackageManifest/PluginManifest 解析与校验 | `PackageManifest`、`PluginManifest`、`ParseManifest()`、`ValidateManifest()` |
| `allowlist.go` | HookAllowlist 加载、校验、匹配 | `HookAllowlist`、`LoadAllowlist()`、`IsHookAllowed()`、`ApplyAllowlist()` |
| `state.go` | 状态机定义与转换 | `PackageState` 枚举、`StateMachine`、`Transition()`、`CanTransition()` |
| `storage.go` | 本地状态持久化 | `PackageStorage`、`SaveState()`、`LoadState()`、`ListInstalled()` |
| `ratelimiter.go` | 三级限速器 | `RateLimiter`、`NewRateLimiter()`、`Allow()`、`CheckAndDisable()` |
| `manager.go` | 生命周期编排（精简后约200行） | `Install()`、`Uninstall()`、`DisableByPolicy()`、`GetStatus()` |

#### 4.2.2 状态机

`state.go` 定义显式状态机：

```
状态枚举:
  pending, downloading, verifying, checking_allowlist,
  installing, active, degraded, disabled_by_rate,
  disabled_by_policy, signature_failed, blocked_by_hook_allowlist,
  load_failed, uninstalled, rolled_back, review_rejected

合法转换:
  pending → downloading
  downloading → verifying | load_failed
  verifying → checking_allowlist | signature_failed
  checking_allowlist → installing | blocked_by_hook_allowlist
  installing → active | load_failed
  active → degraded | disabled_by_rate | disabled_by_policy | uninstalled
  degraded → disabled_by_rate | disabled_by_policy | uninstalled
  disabled_by_rate → disabled_by_policy | uninstalled
  disabled_by_policy → uninstalled
  rolled_back → uninstalled
  review_rejected → pending (允许重新提交构建)
```

每个转换记录时间戳和原因，持久化到 `storage.go`。

#### 4.2.3 限速器

`ratelimiter.go` 实现三级令牌桶：

```go
type RateLimiter struct {
    pluginLimiters  map[string]*rate.Limiter  // per plugin_id, 默认 1000/s
    typeLimiters    map[string]*rate.Limiter   // per event_type, 默认 500/s
    pidLimiters     map[int]*rate.Limiter      // per pid, 默认 100/s
    mu              sync.Mutex
    disableCallback func(packageID, reason string)  // 超限30s触发
    exceedStart     map[string]time.Time            // 超限开始时间
}
```

- `Allow(pluginID, eventType, pid int) bool`: 三级都通过才放行
- 持续超限30s → 调用 `disableCallback` → 状态变为 `disabled_by_rate`
- 限速值可通过 `package.yaml` 的 `limits` 字段覆盖

#### 4.2.4 perf fallback

`ebpf/plugin/loader.go` 修改 `LoadPlugin()`：

1. 先尝试 `ringbuf` attach
2. 若失败且错误为 "ringbuf not supported"（内核 < 5.8），尝试 `perf buffer` attach
3. 记录使用的 transport 到 `LoadedPlugin.Transport` 字段
4. 两种都失败才返回错误

#### 4.2.5 Correlation TreeKey

`correlation/process_context.go` 新增：

```go
type ProcessContext struct {
    PID     int
    PPID    int
    UID     int
    GID     int
    Comm    string
    TreeKey string  // 新增: host_id + nearest_stable_ancestor_pid
}
```

- `ComputeTreeKey(hostID string, procCtx ProcessContext) string`
- 从 `/proc/{pid}/status` 读取 PPid 链，找到最近稳定祖先（session leader 或 init）
- 无法解析时 fallback `host_id + pid`
- `getCorrelationKey()` 支持 `by: pid_tree` 使用 TreeKey

#### 4.2.6 alert 上报接通

Alert 上报分两段：

1. **Agent → Server**: 复用现有 `ReportEvent` RPC，`event_type = "correlation_alert"`，包含 `package_id`/`correlation_rule_id`/`evidence_chain` JSON
2. **Server → API Server**: 通过 `api_server_comm.proto` 的 `ReportCorrelationAlert` RPC 转发（L1 3.1.2 定义）

`agent/cmd/agent/main.go` 修改：

const PERMISSIONS: Record<Role, string[]> = {
  security_analyst: ['view', 'draft', 'ai_generate'],
  security_developer: ['view', 'draft', 'ai_generate', 'build', 'review', 'sign'],
  admin: ['view', 'draft', 'ai_generate', 'build', 'review', 'sign', 'enable', 'disable', 'uninstall', 'rollback', 'allowlist'],

## 8. 风险与缓解

| 风险 | 缓解措施 |
|------|----------|
| Proto 变更可能破坏现有客户端 | 保持旧字段，新增字段用新编号；gRPC 方法新增而非替换 |
| Agent 重构可能引入回归 | 先写测试用例，再重构；每步验证 |
| 限速器可能误杀正常流量 | 限速值可配置；超限30s才禁用，非立即 |
| 角色权限可能影响现有用户 | 默认角色为 admin（向后兼容）；迁移脚本设置现有用户为 admin |
| Server gRPC 改造需 api-server 同步 | L1 先对齐 Proto，L2/L3 同步改造 |
