## 2. 产品概述

### 2.1 产品定位

Aegis智能主机安全系统是一个面向企业级运维和安全团队的全方位主机安全管理平台。系统融合大语言模型（LLM）的智能分析能力与Agent的自动化执行能力，实现从基线合规检查到漏洞智能修复的完整安全运营闭环。

### 2.2 核心价值主张

- **智能基线管理**: 自动化解析安全基线文档，生成可执行检查脚本
- **漏洞智能修复**: 一键扫描软件漏洞，LLM生成精准修复方案
- **全流程闭环**: 从发现到验证再到修复，覆盖安全运营全生命周期
- **可视化运营**: 清晰的任务追踪、进度展示和结果统计

### 2.3 目标用户

| 用户角色 | 核心需求 | 使用场景 |
|:---|:---|:---|
| 系统管理员 | 主机资产管理、合规检查 | 批量主机纳管、定期基线检查 |
| 运维工程师 | 自动化运维、故障修复 | 漏洞修复、配置修复 |
| 安全工程师 | 漏洞管理、安全合规 | 漏洞扫描、POC验证、修复方案制定 |
| 安全合规专员 | 合规审计、报告生成 | 基线合规审计、漏洞报告 |

### 4.4 页面四：智能漏洞检查与修复（核心新功能）

**页面路径**: `/vulnerability`

#### 4.4.1 功能目标

通过智能化的软件漏洞扫描和修复功能，帮助用户快速发现主机上的已知CVE漏洞，并提供一键修复能力。

#### 4.4.2 界面布局

页面采用上下布局：

- **顶部操作区**: 主机选择器、一键扫描按钮、筛选条件
- **中部数据区**: 漏洞列表表格（核心展示区域）
- **底部统计区**: 漏洞统计卡片（按严重程度分布）

#### 4.4.3 功能模块详细说明

##### 4.4.3.1 一键扫描功能

**用户操作**: 用户在主机选择器中选择目标主机，点击"一键扫描"按钮。

**后端处理流程**:

1. **软件清单采集**: 
   - 系统向选中主机的Agent下发指令
   - Agent执行命令收集已安装软件列表
   - CentOS/RHEL系统: `rpm -qa --qf "%{NAME}\t%{VERSION}\t%{RELEASE}\n"`
   - Ubuntu/Debian系统: `dpkg-query -W -f='${Package}\t${Version}\n'`

2. **数据汇总**: 
   - 后端接收所有主机的软件清单数据
   - 按软件名称和版本进行聚合去重

3. **LLM智能分析**:
   - 后端将软件清单发送至LLM
   - LLM分析每个软件的版本，识别已知CVE漏洞
   - LLM返回结构化数据，包含：CVE编号、严重程度、漏洞描述、影响版本范围

4. **结果关联**:
   - 系统将CVE与具体主机关联
   - 生成漏洞实例记录，写入数据库

5. **前端展示**:
   - 扫描完成后，漏洞列表自动刷新
   - 显示新发现的漏洞条目

**扫描状态提示**:

| 阶段 | 提示文案 | 预计时长 |
|:---|:---|:---|
| 软件采集 | "正在收集主机软件清单..." | 10-30秒 |
| CVE分析 | "正在分析漏洞数据..." | 20-60秒 |
| 结果生成 | "正在生成漏洞报告..." | 5-10秒 |

##### 4.4.3.2 漏洞列表展示

漏洞列表是此页面的核心组件，采用Element Plus的ElTable实现。

**表格列定义**:

| 列名 | 字段 | 宽度 | 展示方式 | 说明 |
|:---|:---|:---|:---|:---|
| CVE编号 | `cve_id` | 150px | 纯文本，蓝色链接样式 | 如CVE-2021-44228，点击可跳转详情 |
| 严重程度 | `severity` | 120px | Tag标签，颜色区分 | Critical(红色)、High(橙色)、Medium(黄色)、Low(蓝色) |
| 漏洞原理 | `description` | 250px | 截断显示，悬浮提示 | 超过50字符截断，悬浮显示完整描述 |
| 受影响组件 | `affected_packages` | 200px | 纯文本 | 显示软件名和版本，如"log4j 2.14.1" |
| 影响主机 | `affected_hosts` | 180px | 数字+展开按钮 | 显示受影响主机数量，点击展开列表 |
| 发现时间 | `discovered_at` | 150px | 格式化时间 | 如2026-03-13 10:30:00 |
| 操作 | `actions` | 200px | 按钮组 | "一键修复"、"POC验证" |

**严重程度颜色定义**:

| 级别 | 分值范围 | 颜色 | Tag样式 |
|:---|:---|:---|:---|
| Critical | 9.0-10.0 | #F56C6C | danger |
| High | 7.0-8.9 | #E6A23C | warning |
| Medium | 4.0-6.9 | #909399 | info |
| Low | 0.1-3.9 | #67C23A | success |

**筛选功能**:

- **严重程度筛选**: 多选下拉框，可选择多个级别
- **时间范围筛选**: 日期选择器，筛选发现时间
- **关键字搜索**: 搜索框，支持CVE编号、软件名称模糊匹配

**分页配置**:

- 默认每页10条
- 支持切换：10/20/50/100条每页
- 显示总条数和当前范围

##### 4.4.3.3 一键修复功能

**用户操作**: 用户在漏洞列表中点击某行的"一键修复"按钮。

**交互流程**:

1. **修复确认对话框**:
   - 弹窗显示CVE基本信息（编号、严重程度、描述）
   - 显示受影响主机列表（多选，默认全选）
   - 显示"生成修复脚本"按钮

2. **脚本生成**:
   - 用户点击"生成修复脚本"
   - 后端发送请求至LLM，参数包括：
     - CVE编号和详细信息
     - 目标主机操作系统类型和版本
     - 已安装的软件版本
   - LLM生成针对性的修复脚本

3. **脚本预览与确认**:
   - 生成的脚本显示在对话框的代码编辑器中
   - 使用等宽字体，语法高亮显示
   - 用户可查看脚本内容，确认无误后点击"确认执行"
   - 用户可点击"重新生成"让LLM生成新的修复方案

4. **任务下发与执行**:
   - 后端将修复脚本下发至目标主机的Agent
   - Agent在主机上执行脚本
   - 后端实时收集执行结果和日志

5. **结果反馈**:
   - 执行完成后，弹窗显示执行结果摘要
   - 成功：显示"修复成功"，建议"重新扫描验证"
   - 失败：显示错误日志，提供"查看详情"和"重新修复"选项

**修复脚本示例**:

```bash
#!/bin/bash
# CVE-2021-44228 Log4j 漏洞修复脚本
# 目标系统: CentOS 7

echo "开始修复 Log4j 漏洞..."

# 备份原有jar文件
find / -name "log4j-core-*.jar" -type f 2>/dev/null | while read jar_file; do
    echo "备份: $jar_file"
    cp "$jar_file" "$jar_file.bak.$(date +%Y%m%d%H%M%S)"
done

# 更新至安全版本
yum update -y log4j

# 验证修复结果
if rpm -q log4j | grep -q "2.17"; then
    echo "修复成功: Log4j已更新至安全版本"
    exit 0
else
    echo "修复失败: 版本更新未成功"
    exit 1
fi
```

##### 4.4.3.4 POC验证功能

**用户操作**: 用户在漏洞列表中点击"POC验证"按钮。

**交互流程**:

1. **验证配置对话框**:
   - 显示CVE编号和描述
   - 显示受影响主机列表（单选，默认第一个）
   - 显示"生成POC脚本"按钮
   - 说明文字："POC验证用于确认漏洞是否存在，脚本经过安全设计，不会对系统造成破坏"

2. **POC脚本生成**:
   - 后端发送请求至LLM，参数包括：
     - CVE编号
     - 目标主机操作系统信息
     - 已安装的软件版本
   - LLM基于知识库检索该CVE的公开POC信息
   - LLM生成安全、非破坏性的验证脚本

3. **脚本预览**:
   - 生成的POC脚本显示在代码编辑器中
   - 显示风险提示："此脚本仅用于验证漏洞是否存在，不会修改系统配置"
   - 用户确认后点击"开始验证"

4. **验证执行**:
   - Agent在目标主机上执行POC脚本
   - 脚本通常执行以下操作：
     - 检查软件版本是否在漏洞影响范围内
     - 尝试触发漏洞特征（如特定请求、环境变量检测）
     - 记录验证结果，不造成实际损害

5. **结果展示**:
   - **验证通过（漏洞存在）**: 显示"漏洞已确认存在"，红色警示，建议立即修复
   - **验证未通过（漏洞不存在）**: 显示"未检测到漏洞"，绿色提示，可能原因：已修复、版本不在影响范围
   - **验证失败（脚本执行错误）**: 显示错误日志，可重新验证

**POC脚本示例**:

```bash
#!/bin/bash
# CVE-2021-44228 Log4j POC验证脚本
# 安全说明: 此脚本仅检测特征，不执行恶意代码

echo "开始验证 Log4j 漏洞..."

# 检测log4j版本
LOG4J_VERSION=$(rpm -q log4j 2>/dev/null | grep -oP '\d+\.\d+' | head -1)

if [[ -z "$LOG4J_VERSION" ]]; then
    echo "未检测到log4j安装"
    exit 0
fi

echo "检测到log4j版本: $LOG4J_VERSION"

# 版本比对 (< 2.15.0 存在漏洞)
if [[ $(echo "$LOG4J_VERSION < 2.15" | bc) -eq 1 ]]; then
    echo "漏洞验证结果: 存在 (版本 $LOG4J_VERSION 低于安全版本2.15.0)"
    exit 1
else
    echo "漏洞验证结果: 不存在 (版本 $LOG4J_VERSION 已修复)"
    exit 0
fi
```

### 5.2 关键决策点

| 决策点 | 用户选择 | 系统响应 |
|:---|:---|:---|
| 扫描结果为空 | 重新选择主机扫描 | 清空当前结果，重新开始流程 |
| 扫描发现漏洞 | 点击POC验证 | 生成并执行POC脚本，显示验证结果 |
| POC验证确认 | 点击一键修复 | 生成修复脚本，执行修复 |
| 修复失败 | 查看错误日志 | 显示详细错误信息，支持重新修复 |
| 修复成功 | 重新扫描验证 | 跳转回扫描页面，建议重新扫描确认 |

### 5.3 典型用户场景

#### 场景一：日常漏洞巡检

1. 安全工程师每周一进入漏洞检查页面
2. 选择所有生产环境主机
3. 点击一键扫描
4. 等待约1-2分钟获取结果
5. 筛选出Critical和High级别漏洞
6. 对高危漏洞逐一进行POC验证
7. 确认存在的漏洞立即执行一键修复
8. 修复完成后重新扫描验证
9. 生成本周漏洞报告

#### 场景二：应急响应

1. 接到新CVE公开通知（如Log4j漏洞）
2. 快速进入漏洞检查页面
3. 选择所有主机进行扫描
4. 在结果中搜索该CVE编号
5. 发现受影响主机后立即修复
6. 修复完成后POC验证确认
7. 导出受影响主机清单上报

## 7. 异常处理 (Exception Handling)

### 7.1 异常分类与处理策略

| 异常类型 | 发生场景 | 前端表现 | 用户引导 |
|:---|:---|:---|:---|
| LLM超时 | 生成CVE列表或修复脚本超时 | 显示超时提示，提供重试按钮 | 建议检查LLM服务状态或稍后重试 |
| 脚本执行失败 | 修复脚本在Agent上执行出错 | 显示错误详情，包括stderr | 提供"重新生成脚本"和"手动修复"选项 |
| Agent离线 | 扫描或修复时Agent断开连接 | 显示Agent离线状态 | 建议检查Agent服务或网络连接 |
| 网络错误 | 前后端通信中断 | 显示网络错误提示 | 建议刷新页面或检查网络 |
| LLM生成失败 | LLM返回格式错误或无结果 | 显示生成失败原因 | 提供重新生成选项 |
| 权限不足 | 脚本执行需要更高权限 | 显示权限错误 | 建议以root用户运行Agent |

### 7.2 详细异常处理方案

#### 7.2.1 LLM响应超时

**触发条件**:
- CVE分析请求超过60秒无响应
- 脚本生成请求超过30秒无响应

**前端表现**:
```
组件: ElMessageBox，type="warning"
标题: "请求超时"
内容: 
  "AI服务响应超时，可能原因：
   • LLM服务负载过高
   • 网络连接不稳定
   • 请求数据量过大"
按钮: [取消] [重新尝试]
```

**后端处理**:
- 设置请求超时时间：CVE分析60秒，脚本生成30秒
- 超时后中断请求，返回408状态码
- 记录超时日志，包含请求参数和时间戳

**用户引导**:
1. 点击"重新尝试"：重新发送请求
2. 点击"取消"：返回上一状态
3. 建议用户：检查LLM配置中的Base URL是否可达

#### 7.2.2 脚本执行失败

**触发条件**:
- 修复脚本返回非0退出码
- 脚本执行过程中抛出异常
- Agent执行超时（默认5分钟）

**前端表现**:
```
组件: ElDialog
标题: "修复失败"
内容区域:
  ┌─────────────────────────────────────┐
  │ 错误摘要:                            │
  │ 命令未找到: apt-get                  │
  │                                     │
  │ [查看完整日志]                       │
  │ ┌─────────────────────────────────┐ │
  │ │ stderr:                         │ │
  │ │ bash: apt-get: command not found│ │
  │ │ ...                             │ │
  │ └─────────────────────────────────┘ │
  └─────────────────────────────────────┘
按钮: [关闭] [重新生成脚本] [手动修复]
```

**错误分类与提示**:

| 错误类型 | 识别关键字 | 提示文案 |
|:---|:---|:---|
| 命令不存在 | command not found | "目标系统缺少必要命令，请检查系统环境" |
| 权限不足 | Permission denied | "脚本执行权限不足，请确保Agent以root运行" |
| 网络问题 | Connection refused | "无法连接软件源，请检查网络或代理配置" |
| 依赖冲突 | conflicts with | "软件包存在依赖冲突，建议手动解决" |
| 磁盘不足 | No space left | "磁盘空间不足，请清理后再试" |
| 超时 | timeout | "脚本执行超时，可能任务过于复杂" |

**用户引导**:
1. "重新生成脚本"：让LLM基于错误信息生成新的修复方案
2. "手动修复"：跳转到文档页面，提供手动修复指南
3. 显示"修复建议"输入框，用户可补充信息辅助LLM修复

#### 7.2.3 Agent断开连接

**触发条件**:
- 任务执行过程中Agent心跳超时（超过30秒未上报）
- Agent主动断开WebSocket连接
- 任务下发时Agent已离线

**前端表现**:

**场景A: 扫描时断开**:
```
组件: ElNotification，type="error"
标题: "主机连接中断"
内容: "192.168.1.100 (web-server-01) 在扫描过程中离线"
操作: 显示"查看详情"按钮，跳转主机列表
```

**场景B: 修复时断开**:
```
组件: ElMessageBox，type="error"
标题: "修复中断"
内容: 
  "以下主机在执行修复任务时失去连接：
   • 192.168.1.100 (web-server-01)
   • 192.168.1.101 (web-server-02)
  
  可能原因：
   • Agent服务异常退出
   • 网络连接中断
   • 主机重启"
按钮: [稍后处理] [重新连接并重试]
```

**后端处理**:
- 维护Agent心跳检测（每10秒一次）
- 检测到离线后，标记相关任务为失败状态
- 保存已执行部分的日志

**用户引导**:
1. 引导用户检查Agent状态：
   ```bash
   systemctl status aegis-agent
   ```
2. 如需重新安装Agent，提供安装命令
3. 任务支持"断点续修"：已修复的主机跳过，仅修复失败的主机

#### 7.2.4 无可用修复方案

**触发条件**:
- LLM无法生成有效的修复脚本（如CVE太新，无公开修复方案）
- 修复脚本验证失败（语法错误、命令不存在等）

**前端表现**:
```
组件: ElAlert，type="warning"
标题: "暂无可用的自动修复方案"
内容:
  "AI暂时无法为此CVE生成有效的自动修复脚本。可能原因：
   • 该CVE为0day漏洞，暂无官方修复方案
   • 您当前的系统版本过旧，官方已停止维护
   • 漏洞需要手动介入修复"

建议操作:
• 查阅官方安全公告获取修复指南
• 考虑升级系统版本
• 联系安全团队获取专业支持

[查看CVE详情] [联系技术支持]
```

### 7.3 全局错误处理

#### 7.3.1 错误提示规范

**Toast提示** (ElMessage):
- 使用场景: 操作成功/失败的一般性提示
- 持续时间: 3秒
- 位置: 顶部居中
- 成功: type="success"，绿色勾选图标
- 失败: type="error"，红色错误图标

**通知提示** (ElNotification):
- 使用场景: 需要用户关注但不必立即处理的异常
- 持续时间: 不自动关闭或10秒
- 位置: 右上角
- 支持操作按钮

**对话框** (ElMessageBox / ElDialog):
- 使用场景: 需要用户决策或展示详细信息的异常
- 阻塞式交互，必须用户响应

#### 7.3.2 错误日志收集

**前端日志**:
```javascript
// 错误上报
const reportError = (error, context) => {
  const payload = {
    userAgent: navigator.userAgent,
    url: window.location.href,
    error: error.message,
    stack: error.stack,
    context: context, // 操作上下文
    timestamp: new Date().toISOString()
  };
  // 发送到后端日志服务
  fetch('/api/v1/logs/frontend', {
    method: 'POST',
    body: JSON.stringify(payload)
  });
};
```

**后端日志**:
- 使用zap日志库记录所有API请求和响应
- 错误日志包含：请求ID、用户ID、错误详情、堆栈信息
- 日志保存路径: `/var/log/aegis/`
- 日志保留策略: 7天轮转

## 8. 验收标准 (Acceptance Criteria)

### 8.1 功能验收标准

#### 8.1.1 一键扫描功能 (AC-001)

**AC-001.1**: 主机选择
- 用户可以在下拉框中选择一台或多台主机
- 支持全选和清空操作
- 未选择主机时，一键扫描按钮禁用

**AC-001.2**: 扫描触发
- 点击"一键扫描"按钮后，按钮进入加载状态
- 系统向后端发送扫描请求，包含选中的主机ID列表
- 后端返回任务ID，前端开始轮询扫描状态

**AC-001.3**: 扫描状态展示
- 扫描过程中显示进度提示（采集软件清单 → AI分析 → 生成报告）
- 每个阶段显示预计剩余时间
- 支持取消扫描操作

**AC-001.4**: 扫描结果展示
- 扫描完成后，漏洞列表自动刷新显示结果
- 列表按严重程度降序排列（Critical在前）
- 显示扫描总耗时和发现漏洞数量

**AC-001.5**: 扫描结果验证
- 验证CVE编号格式正确（CVE-YYYY-NNNNN）
- 验证严重程度与CVE官方评分一致（误差±0.1）
- 验证受影响主机数量准确

#### 8.1.2 漏洞列表展示 (AC-002)

**AC-002.1**: 列表基本功能
- 表格正确显示所有字段（CVE编号、严重程度、漏洞原理、受影响组件、主机数量、发现时间、操作）
- 支持分页浏览，默认每页10条
- 支持按列排序（严重程度、发现时间）

**AC-002.2**: 严重程度标识
- Critical级别显示红色Tag
- High级别显示橙色Tag
- Medium级别显示灰色Tag
- Low级别显示绿色Tag

**AC-002.3**: 筛选与搜索
- 严重程度筛选支持多选，筛选结果准确
- 搜索框支持CVE编号和软件名称模糊匹配
- 筛选和搜索可以组合使用

**AC-002.4**: 行展开功能
- 点击"主机数量"可以展开查看受影响主机详情
- 展开内容包含主机IP、主机名、当前软件版本
- 展开状态在分页切换时保持

#### 8.1.3 一键修复功能 (AC-003)

**AC-003.1**: 修复对话框
- 点击"一键修复"按钮弹出确认对话框
- 对话框显示CVE基本信息和受影响主机列表
- 主机列表支持多选，默认全选

**AC-003.2**: 脚本生成
- 点击"生成修复脚本"按钮后显示加载状态
- LLM根据CVE和主机OS生成针对性脚本
- 生成时间不超过30秒

**AC-003.3**: 脚本预览
- 生成的脚本显示在代码编辑器中
- 使用等宽字体，支持Shell语法高亮
- 脚本内容包含注释说明和错误处理

**AC-003.4**: 修复执行
- 用户确认后，脚本下发至Agent执行
- 前端实时显示执行进度（主机级别）
- 执行结果（成功/失败）实时反馈

**AC-003.5**: 修复成功标准
- 脚本退出码为0
- 重新扫描后该CVE不再出现
- 修复成功的主机显示绿色成功状态

**AC-003.6**: 修复失败处理
- 脚本退出码非0时标记为失败
- 显示错误日志和失败原因分析
- 提供"重新生成脚本"和"重新执行"选项

#### 8.1.4 POC验证功能 (AC-004)

**AC-004.1**: POC对话框
- 点击"POC验证"按钮弹出验证配置对话框
- 对话框显示安全提示和免责声明
- 主机选择为单选，默认选中第一个

**AC-004.2**: POC脚本生成
- LLM生成安全、非破坏性的验证脚本
- 脚本生成时间不超过20秒
- 脚本包含详细注释说明验证逻辑

**AC-004.3**: POC执行
- Agent在目标主机执行POC脚本
- 执行过程显示进度条
- 执行时间不超过2分钟

**AC-004.4**: 验证结果判定
- 漏洞存在: 脚本检测到漏洞特征，返回确认状态
- 漏洞不存在: 脚本未检测到漏洞，返回安全状态
- 验证失败: 脚本执行出错，返回错误信息

**AC-004.5**: 结果展示
- 验证成功（漏洞存在）显示红色警告图标和"漏洞已确认"文案
- 验证成功（漏洞不存在）显示绿色成功图标和"未检测到漏洞"文案
- 验证失败显示错误详情和重试按钮

### 8.4 安全验收标准

**AC-S01**: API认证
- 所有漏洞相关API需要有效的JWT Token
- 未认证请求返回401状态码

**AC-S02**: 权限控制
- 只有管理员和运维角色可以执行修复操作
- 普通用户只能查看和POC验证
- 权限不足返回403状态码

**AC-S03**: 脚本安全
- 所有LLM生成的脚本在执行前经过白名单校验
- 禁止执行包含rm -rf /等危险命令的脚本
- 脚本在沙箱环境预执行验证

**AC-S04**: 数据安全
- CVE数据在传输过程中使用HTTPS加密
- 敏感操作（修复执行）记录审计日志
- API Key存储在数据库中加密

### 8.5 验收测试用例

#### TC-001: 完整漏洞修复流程

**前置条件**:
- 系统已配置LLM
- 已纳管至少2台CentOS 7主机
- 主机上安装有log4j 2.14.1版本

**测试步骤**:
1. 进入"智能漏洞检查与修复"页面
2. 选择2台主机，点击"一键扫描"
3. 等待扫描完成，验证CVE-2021-44228出现在列表中
4. 点击该CVE的"POC验证"按钮
5. 选择一台主机，生成并执行POC脚本
6. 验证POC结果显示"漏洞存在"
7. 点击"一键修复"按钮
8. 生成修复脚本，预览并确认执行
9. 等待修复完成，验证显示"修复成功"
10. 重新扫描这两台主机
11. 验证CVE-2021-44228不再出现在结果中

**预期结果**: 所有步骤执行成功，漏洞被成功修复

#### TC-002: 异常场景处理

**测试步骤**:
1. 扫描过程中断开一台主机的Agent网络
2. 验证前端显示连接中断提示
3. 修复脚本中注入错误命令（如command_not_exist）
4. 验证修复失败并显示正确错误信息
5. LLM配置错误Base URL，执行扫描
6. 验证显示超时提示和重试按钮

**预期结果**: 所有异常场景均有友好提示和恢复方案
