# 实现计划：工具参数确定性绑定、Mapping 条件执行图、capability 启动强校验

## 根因分析（已通过代码追踪确认）

**关注点 1 — 参数未完全后端化**：`tool_decision_engine.go:638-640` 的 `previous_step` 源只记录来源标记并返回 `nil`（注释称"由调用方在执行时动态注入"，但**无任何注入机制**）。`applyPlanArgs`（`adapter_tool_gateway.go:539-574`）只返回计划编译参数、丢弃模型参数，于是 `Asset.Collection.Get` 的 `task_id`、`Vulnerability.Scan.Status` 的 `scan_id`、`Operation.Get` 的 `operation_id` 等永远缺失 → schema 校验失败。结果提取基础设施已存在（`tool_outcome.go` 的 `OperationRef`/`SideEffects`/`Facts`/`SatisfiesCapabilities`），但提取出的引用**从不回填下一步参数**。`Asset.Collection.Trigger` 还**缺少** `OperationRefFields:["task_id"]`，导致其 `task_id` 不可提取。

**关注点 2 — Mapping 偏"能力集合"**：`ReadonlyCompanionToolNames` 把所有只读轮询配套工具作为**无条件** plan step 注入（`buildPlanSteps`），同时它们又作为 `CompletionTools` 注册给 runtime 异步轮询。`ToolPlanStep.Condition`/`OnSuccess` 字段存在但仅作 objective 文案（`runtime_execution_plan.go:80-82`），不参与执行门控。于是 `*.Status`/`*.Get` 轮询步骤在其生产者未运行/失败/已终态时仍被无条件执行。

**关注点 3 — capability 启动强校验缺失**：`Register`（`tool_registry.go:238-242`）已做唯一性检查，但**只比较原始 `spec.Capability` 字段且仅非空时**。两个 `Capability` 为空但同 `domain+operation` 的工具会经 `syntheticToolCapability`（`tool_capability_mapping.go:115-126`）得到相同合成能力，而注册检查**漏过**。无独立启动校验方法（仅 `ValidateModelFacingEnglish`）。

## 成功标准

1. 生产者结果 → 下一步参数由后端确定性绑定（`operation_id`/`scan_id`/`query_id`/`task_id`/`cve_id`+`script_type`），模型不再为这些 `previous_step` 参数生成值；参数齐全的步骤直接派发。
2. 依赖 `previous_step` 必填参数的只读轮询配套步骤：当生产者未产出引用时被**跳过**（终态 Skipped），不再无条件执行；条件编译进 `ToolExecutionPlan`。
3. 启动时对**解析后**（含合成）capability 做唯一性强校验，冲突则 Fatal；保留 1:1 策略。
4. 现有测试全绿；新增覆盖上述行为的测试通过；`go build ./...`、`make build` 通过；重启 api-server 后智能体模式冒烟通过。

## 范围边界

- **纳入**：单值引用型轮询配套（baseline `operation_id`、漏洞 `scan_id`/`query_id`/`cve_id`+`script_type`、资产 `task_id`）的确定性绑定与条件跳过；Condition 编译进 plan；启动唯一性校验。
- **不纳入（明确后续）**：`Host.Resolve` → `host_ids` 数组型发现绑定（需 Facts 数组聚合，属独立增强，风险与本次不同）；告警模块无轮询配套，仅受益于启动校验。

## 设计

### A. 运行时 previous_step 确定性绑定 — `adapter_tool_gateway.go`
- 给 `AssistantToolGatewayAdapter` 增加并发安全、per-run 的 `priorStepOutcomes map[string]capturedStepOutcome`（key=stepID），含 `operationRef map[string]string`、`sideEffects []map[string]interface{}`、`terminal bool`。
- 在 `Call` 成功路径（含 Accepted/非终态、终态、asyncPoll）`normalizeToolOutcome` 后，按 stepID 捕获/更新 `outcome.OperationRef`/`SideEffects`/`terminal`。
- 新增可测函数 `resolvePreviousStepArgs(stepID, toolName, args)`：在 `Prepare` 中 `applyPlanArgs` 之后执行；据 plan step 的 `ArgSources`，对 `SourceType=="previous_step"` 且仍缺失的参数，按**参数名 == 前序 outcome 的 OperationRef/SideEffects 字段名**匹配（前序倒序、跳过 `type` 键）注入值。参数齐全则直接派发（保持现状）。

### B. 条件跳过 + 条件编译进 plan
- 跳过判定：`Prepare` 解析后，若该 step 存在**必填**（schema `required`）且 `ArgSources` 标记 `previous_step` 的参数仍缺失 → 置 `req.Context["aegis_step_skipped"]=reason`；`Call` 据此返回终态 `OperationSkipped` 的 ToolResponse（不派发、记 skipped outcome、发 onToolResult），runtime 标记步骤完成并继续。级联：被跳过的生产者使其下游参数同样无法解析 → 同样跳过。
- 条件编译：`tool_decision_engine.go` `newToolPlanStep` 中，对含 `previous_step` 必填参数的 step 写入 `Condition`（如 `"requires previous step to produce scan_id"`），使条件图显式进入 `ToolExecutionPlan`。
- 不移除配套 step（baseline 测试要求 `Operation.Get` 为第 3 步、设计文档 8.5），仅由无条件改为条件。

### C. 生产者引用补全 + 启动唯一性校验
- `tools/asset_tools.go`：给 `Asset.Collection.Trigger` 的 `ResultContract` 增加 `OperationRefFields:["task_id"]`（handler 已返回 `task_id`）。
- `tool_registry.go`：新增 `ValidateCapabilityUniqueness() error`，遍历所有工具用 `BuildToolUseContract(tool).Capability` 解析（含合成），断言无重复（大小写不敏感），冲突返回明确错误。`cmd/main.go` 在 `ValidateModelFacingEnglish()` 旁调用，失败 Fatal。实现时先验证当前工具集通过（若存在合成冲突，给相关工具补显式 Capability，而非弱化校验）。

## 测试设计（先写能失败的用例）
1. **previous_step 绑定**：两步 plan，step2 必填 `task_id` 来源 previous_step；step1 结果含 `task_id` → 断言 step2 收到绑定的 `task_id`（非缺失）。
2. **条件跳过**：配套 step 必填 previous_step 参数但无前序 outcome → 断言返回终态 Skipped、未派发。
3. **生产者引用提取**：`Asset.Collection.Trigger` outcome 的 `OperationRef` 含 `task_id`。
4. **启动唯一性**：两个空 Capability 同 domain+operation（合成冲突）→ `ValidateCapabilityUniqueness` 报错；正常集 → nil。
5. **回归**：`TestToolDecisionEngineAllowsRequiredArgFromPreviousStepForAnyTool`（保留 ArgSources 标记）、`TestCapabilityMappingAddsOnlyReadonlyDeclaredCompanions`、baseline 3 步顺序与确定性参数不变。

## 可运维性（daily-program-logging）
- previous_step 解析命中（Debug：session/run/step/参数名/来源step）、跳过（Info：session/run/step/原因）、启动唯一性校验结果（Info 成功 / Fatal 失败）、outcome 引用捕获（Debug）。不记录敏感值，仅记录参数名与来源 step。

## 风险与回滚
- 风险：跳过 ToolResponse 的 runtime 语义。缓解：以 `OperationSkipped` 终态返回并在 agent 模式测试验证；若 runtime 误判阻塞，回退为"仍派发但工具自返回 no-op"（保留条件判定）。
- 风险：合成 capability 冲突致启动失败。缓解：实现时先跑校验，冲突则补显式 Capability。
- 回滚：改动集中、可按文件 revert；无 DB/proto/前端变更。
